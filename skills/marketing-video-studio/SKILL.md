# Marketing Video Studio

Turn a prompt or a URL into a finished MP4 — script, voiceover, visuals, motion,
music and edit — on the self-hosted stack. No external AI service is needed.

The argument is the subject: `marketing-video-studio "Agentic AI SRE"` or a URL to
research first.

## Running inside Paperclip

- Script paths below (`scripts/...`, `references/...`) are relative to this skill's
  directory (the folder containing this `SKILL.md`). Run them from a per-project
  working folder in your issue workspace, e.g.
  `python3 "$SKILL_DIR/scripts/best_of_n.py"`.
- The runtime ships `ffmpeg`/`ffprobe`, Python 3 with Pillow, numpy and boto3, and
  `curl`. Credentials are platform-provided env vars (Step 0). Nothing needs
  installing.
- Deliver the final MP4 (and `storyboard.md`) as issue artifacts using the
  `paperclip` skill's artifact workflow — never a local path alone.
- avatalk renders are slow and GPU-serial. Get sign-off on the storyboard and the
  stills (an issue comment or confirmation) before submitting motion jobs.

## When not to use

- Flat 2D animated explainers with crisp on-screen UI and kinetic type: use
  `motion-explainer-studio`.
- Written copy only (emails, posts, decks) with no video: use `human-write`.

## Read this before running anything

Three reference files carry the details. Load them as needed:

| File | When to read |
|---|---|
| `references/pipeline.md` | Before the first API call — endpoints, auth, the voice registry, cold-start behaviour |
| `references/geometry.md` | **Before any avatalk job** — the crop and frame-rate findings. Skipping this produces distorted or juddering video that looks fine in a still frame |
| `references/assembly.md` | Before ffmpeg work — Ken-Burns, captions, ducking, fades, concat |

`references/geometry.md` is the one that is genuinely non-obvious. Both defects it
describes are invisible in a single frame and only show up in motion, which is how
they ship.

## Pipeline

```
brief ─► 1. research      real facts beat generic copy; real photos beat generated ones
      ─► 2. script        N scenes: VO line · caption · image prompt
      ─► 3. voiceover     best-of-N with STT scoring — narration sets every scene's length
      ─► 4. visuals       real photography where it exists, GenImage elsewhere
      ─► 5. music         one instrumental bed, looped under the VO
      ─► 6. motion        avatalk i2v / talking avatar   [pad first — see geometry.md]
      ─► 7. assemble      captions, ducked music, fades → MP4
```

Captions are burned in by ffmpeg, never generated by the video model. That is a real
advantage over text-to-video tools, which garble on-screen words — so put anything
that must be legible (URLs, dates, prices) in a caption, not in the narration.

## Step 0 — Credentials

The platform provides these as environment variables (Vault → External Secrets →
pod env). Never fetch secrets yourself, write them to disk, or put them in a
manifest or comment.

| Env var | Purpose |
|---|---|
| `MCP_API_KEY` | `X-API-Key` for every `https://mcp.baisoln.com` call |
| `MEDIA_S3_ACCESS_KEY` / `MEDIA_S3_SECRET_KEY` / `MEDIA_S3_BUCKET` / `MEDIA_S3_ENDPOINT` | upload + presign assets for avatalk (`scripts/minio_upload.py`) |

Verify before a long run — a bad key otherwise surfaces as a confusing 401
mid-render:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -H "X-API-Key: $MCP_API_KEY" \
  https://mcp.baisoln.com/gpu-ai/v1/audio/voices   # expect 200
```

If a variable is missing or the check fails, stop and report it to the board; do
not look for other credentials.

## Step 1 — Brief before you build

Ask two or three questions, then commit. The answers that actually change the work:

- **Who is it for?** If the user names more than one audience, ask whether they want
  one video covering all of them or one cut per audience. These are very different
  jobs and the wording ("do it for all three") does not disambiguate. Getting this
  wrong wastes an entire render cycle.
- **What should it feel like?** One adjective is enough to pick a visual style, a
  voice and a music genre — and they must agree with each other. A trailer voice over
  warm documentary footage reads as a mistake.
- **Presenter or narration only?** A presenter costs ~5-8 min of GPU per scene and
  carries pillarboxing (see geometry.md). Narration over b-roll avoids both.

Vary the creative DNA per project so successive videos don't feel templated: narrative
structure, visual style token, voice, music genre, scene count. Keep whatever you pick
consistent *within* a video.

## Step 2 — Research, and prefer real assets

If given a URL, read it before writing a word — real numbers, real programme names and
real dates make copy that generic prose cannot match. Pull the site's own images too.

Real photography usually beats generated stills, but audit it first. Things that
disqualify an image:

- **It's a poster or flyer**, not a photo. Baked-in headline text will fight your
  captions. This is common on events pages and easy to miss if you only read filenames.
- **Under ~1200px wide.** It will look soft once Ken-Burns zooms in.
- **A watermark you can't crop out.** Corner watermarks usually crop away; centred ones
  don't. Cropping a photographer's credit out is a rights question, not a technical
  one — surface it to the user rather than deciding for them.
- **Wrong aspect.** Crop to 16:9 biased away from the watermark.

Look at the images. Filenames and alt text lie.

## Step 3 — Script

Emit per scene: **VO line**, **caption**, **image prompt**. A reliable arc is
Hook → Problem → Reveal → How → Proof → Trust → Payoff → CTA, but it is a default,
not a rule.

Narration drives everything downstream: each scene lasts as long as its VO line, so
the script *is* the runtime budget. Write to the target length rather than trimming
later. Roughly 150 words ≈ 60s at a normal narration pace, but voices differ by 25%
or more — generate one test line with the chosen voice and measure before committing
to a full script.

**Write for TTS.** This is where quality dies:

- No em-dashes or ellipses. They create pauses where cloned voices hallucinate filler.
- Never make the voice speak a URL or a long letter-string. It will mangle it, and a
  best-of-N scorer can even reward a take that silently drops it. Put the URL in the
  caption.
- Spell short acronyms as separate letters; write numbers as words.
- One to three short sentences per scene.
- Hyphenated brand names ("T-Mobile") read better with the hyphen removed.

For multi-audience cuts, changing only the CTA is cheap but shallow. Different
audiences care about genuinely different things — a donor wants stewardship and proof,
a volunteer wants low barrier to entry and belonging. Ask which depth the user wants;
full separate scripts cost a full render cycle each.

**Don't invent claims.** Impact numbers, partner names, tier pricing and certifications
must come from the source. If a line asserts something you could not verify, either cut
it or flag it explicitly when you deliver.

## Step 4 — Voiceover

`scripts/best_of_n.py` generates K takes per scene, transcribes each with
faster-whisper, scores by words inserted or dropped versus the script, and keeps the
cleanest.

```bash
MCP_API_KEY=$KEY VOICE="Jessica" K=6 TEMPO=1.0 python3 scripts/best_of_n.py
```

Cloned voices are stochastic and inject filler at phrase boundaries, so this loop is
what separates broadcast-clean from embarrassing.

**Pick the voice by measurement, not vibes.** `scripts/voice_probe.sh` speaks one line
through several candidates and reports duration plus transcript. Duration is the useful
signal: same line, same words, a 12% spread in pace. Pick for the energy you want.

Reading the scores: a non-zero score is not automatically a defect. Number formatting
("twenty third" heard as "23rd") and unusual proper nouns inflate it. Read the
transcript before re-rolling — if it is verbatim, the take is fine.

If a voice is drawling, its clone may have been built from a messy conversational
reference; pick another voice or ask the operator to rebuild the clone from a clean
clip. Note that the gateway registry metadata does **not** change when the
underlying clone is replaced, so you cannot detect a re-clone by inspecting the
registry. Detect it by
re-running the same script and comparing durations.

## Step 5 — Visuals

`scripts/gen_images.py` renders one 16:9 still per scene from the image prompts. Use the
default model; FLUX-dev times out. Append one shared style token to every prompt so the
set reads as one piece.

## Step 6 — Music

`scripts/build_music.py <seconds> "<tags>"` → `music.mp3`. The body field is **`tags`**,
not `prompt` (a `prompt` body returns 422). Output caps at ~30s; assembly loops it.

## Step 7 — Motion

**Read `references/geometry.md` first.** Summary of what it proves:

- avatalk **centre-crops** any input to a 640×640 square. Feed it a bare 16:9 image and
  you permanently lose the left and right sides. `scripts/pad_for_i2v.py` pads the
  source to 1:1 with a blurred extension so the crop captures the whole frame;
  `scripts/make_live_clips.py` crops the band back out afterwards.
- avatalk **avatar output is 16fps**. Forcing it to 30fps duplicates frames unevenly and
  the mouth judders. `scripts/interpolate_avatar.py` synthesises real intermediate
  frames instead.
- i2v clips are ~3s. Stretching them to cover a 6-10s VO line needs motion
  interpolation, not plain re-timing.

Verify with `scripts/verify_geometry.py`, which correlates a rendered frame against its
source image. Above ~0.95 means the framing survived; ~0.45 means something is stretched.
**Check this numerically.** A distorted frame can look plausible on its own — the only
reliable comparison is against the source, and "contains more of the scene" is not the
same as "correctly proportioned."

Ken-Burns on a crisp real photo is often better than a stretched 3s clip. Motion is not
automatically an upgrade; offer both when the source photography is strong.

## Step 8 — Assemble

`scripts/build_hybrid.py manifest.json` does the whole back half: per-scene clip →
CFR-normalise → concat → duck music → fades → fade to black.

Scene types: `still` (Ken-Burns), `broll` (motion clip + VO), `avatar` (presenter
composited over a blurred background). The manifest is the project's state file —
change one scene's assets, re-run, get a new cut. See the docstring for the schema.

Note `build_hybrid.py` crops b-roll to 16:9 by default, which is correct for square
avatalk output but wrong for clips you have already un-padded to 16:9. Use
`--no-crop` for pre-corrected clips.

## Iterating

Regenerate only what changed. Keep `storyboard.md` and `manifest.json` per project so
feedback maps to a minimal rebuild:

| Feedback | Rebuild | Reuse |
|---|---|---|
| Different presenter | portrait → avatar scenes | all VO, b-roll, music |
| New voice / revoiced clone | all VO → avatar scenes (audio-driven) | b-roll, music, stills |
| Punchier copy in one scene | that VO + maybe its still | everything else |
| Wrong music | `build_music.py` | all video |
| Retarget to another audience | CTA scene, or a full script | b-roll, music, presenter |
| "Make the stills move" | i2v per still (pad first) | VO, captions, timing |

Keep the previous cut as `-v1.mp4` before overwriting, and offer checkpoints after the
storyboard and after the stills — before the expensive renders, not after.

## Delivering

State duration, resolution and where the files are. Then say plainly what is still
imperfect — pillarboxed presenter scenes, slow-motion b-roll, unverified claims in the
copy, unresolved image rights. A user who discovers these themselves after publishing
is far worse off than one who was told.

## Cost awareness

avatalk jobs serialise on one GPU: i2v ~1 min, avatar ~5-8 min, `video.continue` 15-20
min per clip. Nine avatar scenes is roughly an hour of wall clock. Say so up front, and
prefer designs that avoid GPU work when quality is equal — Ken-Burns stills over i2v,
one shared presenter portrait across every cut, one music bed for a whole family of
videos.
